**What each patch does**
- **1 (AA-13):** the macOS `.app`, the unsigned iOS `.app` and the Linux bundle are now uploaded as `ci-proof-…`. A new limb 1c in `assert-release-durable` fails any release-bound upload whose files don't map to a served row or to a row `releaseCarriesFor` says a Release carries. The stage step now creates `downloads/` itself, because `<app>-*` matches nothing today.
- **2 (AA-12 part 1):** `record-deployment.mjs` takes `--artifact <file> --build-number <n>`, hashes the file itself, and writes `payload.artifact = {name, sha256, size, buildNumber}`. It is refused on anything that isn't a store row. Provenance limb 5 requires it on every production record in a `--submit` job.
- **3 (AA-07):** new `tooling/ci/r2-durable-copy.mjs` packs the symbols, puts them under `symbols/<app>/<channel>/<version>+<build>/`, and reads them back. It runs before the store upload in the Play, Windows and Snap submit jobs, and in a new tag-only `durable_symbols` job that `release` needs. The record carries the copy's sha256 via `--symbols-record`. A new DURABLE limb in `assert-obfuscation-coupled` enforces the ordering.
- **5 (AA-21):** new `assert-artifact-size.mjs` runs before each upload. It fails at 80% of the register's `storeSizeLimit` and warns at 2× the median of earlier recorded sizes. The diagnostic `.msix` now uploads only `if: failure()`.
- **6 (AA-27):** §3 of `RELEASE-RUNBOOK.md` is now a block generated by `gen-release-carries.mjs` from `release-manifest.mjs` and the register, with `--check` in `ci.yml`. The superseded §3a/§3b tables and the layered status text are deleted.

**Deviations, seams, and what I could not do**
1. **Patch 4 not done.** It changes `release.json`'s schema, `--emit-assets` and every submit job's download path, and is too big to land safely alongside the rest.
2. **Nothing was already fixed at BASE.** The cited seams matched the code, and the base guard passed with the macOS `.app` still in `<app>-*`.
3. **R2 credentials.** I couldn't read `CLOUDFLARE_API_TOKEN`'s scope here, so I took the owner path:
   - The register declares two new secrets, `R2_RELEASE_ACCESS_KEY_ID` and `R2_RELEASE_SECRET_ACCESS_KEY`, plus a `releaseStore` block: bucket `nikatru-release-store` (a name I chose), `pendingUntil: 2026-11-30`, and the owner step.
   - Until that date a missing credential warns and records `stored: false`; after it, the job fails.
   - The scopes text for `research/…/r2-release-token-scopes.md`: an R2 API token with Object Read & Write on bucket `nikatru-release-store` only, no account-wide permission. Its Access Key ID and Secret Access Key go into the two secrets above.
4. **Bucket not created, lifecycle not declared.** The local writer creates the bucket with the lead's token and adds the ADR draft's lifecycle, which I don't have.
5. **The new R2 secrets are read in two kinds of job.** The submit jobs are bound to `store-publish`. `durable_symbols` has no `environment:` (an environment there would put an approval on every tag run). The brief's environment-bound rule was about the deploy credential; please confirm the same is acceptable for this bucket-scoped token.
6. **Tag-run key segment.** In `durable_symbols` the `<channel>` part of the key is the symbols artifact's lane (`linux-android`, `windows`, `apple`), not a channel id. Each artifact holds several channels' directories.
7. **Size limits:**

   - Microsoft Store: 25 GB per package.
   - Snap: `null` with a reason, because the docs state no limit.
   - Apple rows: none, since neither has a submit lane.
   - I could not measure real artifact sizes here (no builds), so there are no numbers for platform-state.
