# `submit-snap.yml`

The prose that used to live inside `.github/workflows/submit-snap.yml`. The workflow keeps a
one-line `# why:` on each non-obvious decision; everything that explains,
retracts or records a measurement is here. Read `docs/ci/README.md` first —
it carries the rules every workflow in this repository has to obey.

## File header

### above `on:`

[pipeline D-10] limb (i) — "a submission script exists AND RESOLVES TO A STEP
IN A WORKFLOW, parsed not grepped". This workflow is the step it resolves to.
tooling/channel-register.json's linux-snap row names this file and this job in
its `submission` block — and, since 2026-08-09, in its `lane` block too, because
this is now the job that EMITS the format the row accepts.

🔴 DISPATCH-ONLY, AND THAT IS THE CORRECT SHAPE WHILE `served: false`.
The channel is deferred by [ADR 015] until there is revenue — the web build
already serves Linux users at $0 — and the one owner action it needs
(OWNER_QUEUE A-6) is claiming the global snap name.

── WHAT CHANGED ON 2026-08-09, because it changes what a green run here means ─
⚠️ THIS JOB USED TO SAY "IT DOES NOT BUILD A .snap, AND THAT IS NOT A SHORTCUT",
and its own TODO named the condition under which that stopped being true: "There
is no `snapcraft.yaml` in this repository … When the recipe lands, add the build
to THIS job and drop `--allow-missing-artifact` from the step below, in the same
increment." The recipe landed on 2026-08-08 — it is GENERATED by
tooling/release/generate-snapcraft.mjs rather than committed — so this is that
increment. The job now compiles the Linux bundle, derives the recipe from it,
packs a real .snap, and validates THAT rather than validating a listing beside
an artifact nobody could produce.

`--allow-missing-artifact` is gone with it. Keeping the flag once a .snap exists
would be the shape submit-play.yml spent months in: a dry run reporting the
submission path healthy while never touching the one output the channel accepts.

── WHY `--destructive-mode` AND NOT LXD ────────────────────────────────────
✅ `snapcraft pack --destructive-mode` is "Build in the current host" and
`--use-lxd` is "Build in a LXD container" (https://ubuntu.com/docs/snapcraft/
stable/reference/commands/pack/, fetched 2026-08-09). The constraint that
decides between them is the same document's build-environment guidance: "The
build environment should match the snap base."

The recipe's `base` is DERIVED from the runner build-platforms.yml compiles the
bundle on — `ubuntu-24.04` → `core24`. This job runs on the same label, so the
host IS the matching environment and a container would only reproduce it more
slowly: installing and initialising a daemon, joining a group mid-job, and
pulling a base image, to arrive at the environment the runner already is.

⚠️ LXD IS NOT LISTED ON THE ubuntu-24.04 IMAGE and that is an ABSENCE OF
EVIDENCE, stated as one: actions/runner-images' Ubuntu2404-Readme.md (fetched
2026-08-09) enumerates Docker, Podman and Buildah and names no LXD. A README
omission is not a proof of absence, so this is a reason to prefer the path that
needs neither, not a claim that `--use-lxd` would fail.

🔴 THE COUPLING THAT BUYS IS REAL AND IS ENCODED, NOT NOTED. Two workflows now
name a runner label for one snap: build-platforms.yml decides the `base`, this
file decides the host that packs against it. Move either alone and the app links
against libraries it did not build with — a failure with no diagnostic, because
a snap that mismatches its base installs and then misbehaves at runtime. The
`--pack-runner` argument below is what compares them, and it fails the job.

── WHAT ACTUALLY STOPS AN UPLOAD, MEASURED BY RUNNING IT ───────────────
🔴 THIS BLOCK SAID "`--submit` REFUSES WITH UNVERIFIED" UNTIL 2026-08-20 AND
THAT WAS THE WRONG REASON. submit-snap.mjs really does run
`snapcraft upload <snap> --release=<channel>` (:985) — the verbs are sourced.
Run on 2026-08-20 with the CI markers set, the actual refusal was:

    FAIL no job in .github/workflows/submit-snap.yml invokes
         `submit-snap.mjs --submit`.

The refusal was STRUCTURAL, not epistemic: the script requires this workflow to
declare the job that submits, and none did. Two documents disagreed about this
— the register's linux-snap row says the script "refuses to guess", this
header said UNVERIFIED — and NEITHER named the real gate. That is the
recorded lesson of this repo applied to itself: do not trust a workflow header
over the script it invokes; run it.

⚠️ SO ADDING THE `submit` JOB BELOW LIFTS THAT REFUSAL, DELIBERATELY. What
stops an upload now is the next gate in line and it is a real one: no
SNAPCRAFT_STORE_CREDENTIALS secret exists, so the job fails naming the missing
credential. Beyond that sits OWNER_QUEUE A-6, the GLOBAL snap-name claim, which
is irreversible and is the owner's. Snap auto-updates SILENTLY, so a wrong
revision does not fail cleanly — it lands on real machines. Hence the typed
`confirm`, the `store-publish` environment with its required reviewer, and a
job that rebuilds and re-gates the artifact it is about to send.

### above `listing_url:`

── 🔴 [10]D-9 · THE ADDRESS THE LEDGER ROW WILL CARRY ──────────────────
record-deployment.mjs REFUSES a store environment with no
`--listing-url`, and this input is where that value comes from — asked of
the same human, in the same act, as `confirm`.

⚠️ IT IS NOT DERIVED, AND THE REASON IS THAT NOTHING IN THIS REPO KNOWS IT
YET. catalog/apps.json carries `listings.linux: null`, and on this channel
the gap is not merely an unmade console entry: OWNER_QUEUE A-6 is
`snapcraft register <name>`, a claim on a GLOBAL namespace that has not
been made. Writing `https://snapcraft.io/<name>` here would assert a page
that does not exist and put a second copy of the snap name in a workflow
file, when the name has exactly one home — the recipe generated by
tooling/release/generate-snapcraft.mjs. The day catalog/apps.json holds a
real listing URL, this input becomes a default read from there.

The submit job REFUSES an empty or non-https value BEFORE it uploads.

assert-gate-passed.mjs POLLS for up to its own 1200 s default (this call

cancellation. Kept byte-identical in all five `gate:` jobs. [pipeline F-5b]

## The credential expiry guard — 2026-09-07

**Appended, not rewritten.**

An exported Snap Store login carries a lifetime. `snapcraft export-login`,
verbatim: `--expires  Date/time (in ISO 8601) when this exported login expires.`
When it lapses, `snapcraft upload` fails at the one moment a release is in
flight, and until 2026-09-07 nothing in this repository said a word beforehand.

`tooling/release/submit-snap.mjs` now grades the credential in both modes:

| state | verdict |
|---|---|
| `SNAPCRAFT_STORE_CREDENTIALS` absent | **print** on `--dry-run` (owner-gated work, [pipeline C-6]); **fail** on `--submit` |
| present, `SNAPCRAFT_STORE_CREDENTIALS_EXPIRES` absent | **fail** — unknown must never read as fine |
| present, expiry not a readable ISO 8601 date | **fail** — an unreadable expiry is not a long one |
| present, expiry less than **30 days** away (or past) | **fail** |
| present, expiry 30 days or more away | ok, printing the date and the margin |

Every refusal prints the exact owner step:

```
snapcraft export-login --snaps <snap-name> --acls package_push,package_release \
  --expires <YYYY-MM-DDTHH:MM:SSZ> credentials.txt
```

…then the file contents go into `SNAPCRAFT_STORE_CREDENTIALS` and the same date
into `SNAPCRAFT_STORE_CREDENTIALS_EXPIRES`.

### Why a declared date and not the blob

The exported credential's internal format is documented on no page fetched. This
file already refuses to parse `snapcraft whoami` for exactly that reason — its
output format is undocumented — so parsing the blob for an `expires` field would
break that rule one command over to save one environment variable. What *is*
sourced is the flag that sets the date, so the date is recorded beside the
credential by the same hand in the same act. The runbook makes them one step.
