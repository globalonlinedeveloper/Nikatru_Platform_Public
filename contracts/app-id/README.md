# `contracts/app-id/` — the app id rule

An `app_id` becomes a Worker name, a D1 database name, a DNS label, a Dart package, an Android
`applicationId` and an Apple bundle id. The two store ids cannot be changed after the first
upload, so the id is checked against ONE rule before the brick writes anything.

| File | What it is |
|---|---|
| `app-id.js` | the source: `APP_ID_RULE` (pattern `^[a-z][a-z0-9]*$`, 2 to 32 characters), `RESERVED` (Dart reserved words, Java keywords and Kotlin hard keywords, each list citing its spec) and `appIdProblems(id)` |
| `app-id.json` | GENERATED by `generate.mjs` for `tooling/bricks/app/hooks/pre_gen.dart`, which cannot import JavaScript. Never edit it by hand |
| `generate.mjs` | writes `app-id.json`; `--check` exits 1 when the file differs and writes nothing |

**Why 32.** `services/platform/src/config.ts` `APP_ID_PATTERN` serves ids of at most 32
characters and drops a longer one from the served set without an error. That file is a Worker
deploy path, so it is graded here rather than edited.

**What holds it.** `tooling/ci/assert-app-id-contract.mjs`, in `ci.yml` job guards-store:

1. `app-id.json` equals what `generate.mjs` would write;
2. every id the contract accepts passes `config.ts` `APP_ID_PATTERN`;
3. `provision-backend.mjs`, `assert-store-identity.mjs` and `assert-catalog-contract.mjs` import
   `app-id.js`, `pre_gen.dart` reads `app-id.json`, and none of them carries an app-id regex of
   its own;
4. `tooling/app-yaml/schema/app.schema.json`, `privacy.schema.json` and
   `contracts/release.schema.json` accept no id the contract refuses on shape or length.

`ci.yml` job app-brick also stamps `tooling/bricks/app/_probe_bad_id_vars.json` (`habit_tracker`)
and requires mason to fail, name `app_id` and leave no `apps/habit_tracker` behind.
